# Telemetry Transport Lab

A hands-on learning lab for understanding how telemetry signals can be delivered through different communication and streaming transports.

The project implements Python clients for:

- Long Polling
- Server-Sent Events (SSE)
- WebSocket
- gRPC streaming
- Kafka

The main goal is to understand how each transport works from the client side, how data is delivered, and the practical differences between the communication models.

## 1. Project Overview and Learning Objectives

This project was built as a practical exercise to explore different approaches to real-time and asynchronous communication.

### Learning objectives

- Understand different communication and streaming patterns.
- Implement clients for multiple transport mechanisms.
- Understand persistent vs. request-based connections.
- Work with streaming data and telemetry signals.
- Compare WebSocket, SSE, Long Polling, gRPC, and Kafka from a practical perspective.
- Understand how telemetry can be consumed and visualized.

## 2. Long Polling, SSE, WebSocket, gRPC, and Kafka

### Long Polling

The client sends an HTTP request and the server keeps it open until new data is available or the request times out. The client then sends another request.

**Model:** repeated HTTP requests with server-side waiting.

### Server-Sent Events (SSE)

SSE keeps an HTTP connection open and allows the server to continuously send events to the client.

**Model:** persistent, one-way server → client streaming.

### WebSocket

WebSocket establishes a persistent connection that allows both the client and server to send messages.

**Model:** persistent, bidirectional communication.

### gRPC

gRPC uses HTTP/2 and Protocol Buffers to provide strongly typed RPC communication. This project uses server-side streaming, where the client subscribes and receives a continuous stream of signals.

**Model:** structured RPC with streaming.

### Kafka

Kafka uses a broker-based messaging model. Producers publish messages to topics and consumers read them independently, using offsets to track their position.

**Model:** asynchronous, broker-based messaging.

## 3. Signal Model

The project uses different types of telemetry signals to demonstrate how different data can be delivered through different transports.

| Signal | Description | Transport |
|---|---|---|
| **Metrics** | Numeric measurements collected over time, such as CPU, memory, latency, or request rate. | WebSocket |
| **Traces** | Represent the execution path of a request across operations or services. | Long Polling |
| **Logs** | Individual records describing events or activity within an application. | SSE |
| **Profiles** | Data describing application/runtime behavior and resource usage. | gRPC |
| **Events** | Discrete occurrences or messages representing something that happened. | Kafka |

Signals use a common envelope containing information such as an ID, sequence number, timestamp, type, service, severity, and a type-specific payload.

```json
{
  "id": "sig_...",
  "seq": 128,
  "ts": 1752460800000,
  "type": "metric",
  "service": "checkout",
  "severity": "info",
  "payload": {}
}
```

The `type` identifies the kind of telemetry being transported, while the `payload` contains the data specific to that signal type.

## 5. Transport Comparison

| Transport | Connection | Direction | Main characteristic |
|---|---|---|---|
| **Long Polling** | Repeated HTTP requests | Server → Client | Simple request-based approach with server-side waiting |
| **SSE** | Persistent HTTP | Server → Client | Simple server-to-client event streaming |
| **WebSocket** | Persistent | Bidirectional | Full-duplex real-time communication |
| **gRPC** | Persistent stream | Client/Server | Strongly typed RPC over HTTP/2 |
| **Kafka** | Broker-based | Producer → Broker → Consumer | Asynchronous messaging with decoupled producers and consumers |

A simple way to think about the difference:

```text
Long Polling → "Do you have anything new?"

SSE          → "Keep this HTTP connection open and send me events."

WebSocket    → "Keep this connection open; we can both send messages."

gRPC         → "Call this typed service and stream the responses."

Kafka        → "Publish messages to a broker; consumers read them independently."
```

## 6. Observability Comparison

The transports are not interchangeable in terms of their communication model, even though they can all be used to deliver telemetry.

| Aspect | Long Polling | SSE | WebSocket | gRPC | Kafka |
|---|---|---|---|---|---|
| Persistent connection | No | Yes | Yes | Yes | No direct client-to-client connection |
| Server → Client streaming | Yes | Yes | Yes | Yes | Yes, through consumer |
| Client → Server | New HTTP request | No | Yes | Yes | Producer messages |
| Broker required | No | No | No | No | Yes |
| Message persistence | No | No | No | No | Yes |
| Strongly typed schema | No | No | No | Yes | Optional |
| Typical use | Simple polling | Notifications/events | Real-time apps | Service-to-service streaming | Event-driven systems |

This comparison highlights an important distinction: **the transport determines how data moves, while the telemetry signal describes what the data represents.**

## 7. Commands for Running Each Client

Each client can be run independently.

```bash
# Long Polling
python clients/long_polling.py

# SSE
python clients/sse.py

# WebSocket
python clients/websocket_client.py

# gRPC
python clients/grpc_client.py

# Kafka
python clients/kafka_consumer
```

Each client connects to its corresponding Meowmetry endpoint and consumes incoming signals.

## 8. gRPC Protobuf Generation

The gRPC service definition is located at:

```text
proto/signals.proto
```

Generate the Python gRPC modules with:

```bash
python -m grpc_tools.protoc \
  -I proto \
  --python_out=clients \
  --grpc_python_out=clients \
  proto/signals.proto
```

This generates:

```text
clients/signals_pb2.py
clients/signals_pb2_grpc.py
```

The generated modules are then used by the gRPC client to create the service stub and consume the streaming RPC.
